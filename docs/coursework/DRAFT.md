## Введение

Менеджер каталога добавляет товары, меняет цены и остатки, распределяет позиции по категориям. При такой работе возникают ошибки: повторяется артикул, вводится отрицательное количество или выбирается удалённая категория. Программа должна отклонять эти данные и объяснять причину отказа. В курсовой работе разработан модуль, который выполняет перечисленные операции через веб-формы и JSON API, применяя общие правила проверки.

Работа выполняется по дисциплине «Разработка программных модулей» для специальности 09.02.07 «Информационные системы и программирование». Выданное задание определяет операции добавления, просмотра, изменения и удаления товаров, поиск, фильтрацию, сортировку и хранение данных. В качестве документационной основы в задании назван ГОСТ 19.201–78 [1]. Структура и базовое оформление записки приняты по предоставленным методическим указаниям МФЮА [2]. Объём проекта ограничен управлением каталогом: заказы, расчёты с покупателями и доставка не рассматриваются.

При проектировании использованы материалы о типах и классах Python [3], разделении прикладных операций и обработчиков запросов [5], работе с небольшими воспроизводимыми примерами [7]. Для выбора проверок рассмотрены функциональные тесты пользовательских сценариев и тесты отдельных компонентов [6; 8]. В проекте эти виды проверок разделены на тесты базы данных, API и HTML-страниц.

Цель работы — разработать модуль для ведения товаров и категорий интернет-магазина и проверить его работу. Менеджер должен добавлять позиции, менять цены и остатки, искать товары и одновременно применять несколько фильтров. Для этого нужно определить правила каталога, выбрать средства разработки, спроектировать базу и страницы, написать операции и обработку ошибок. Завершающие задачи: подготовить примеры товаров, выполнить тесты и описать обнаруженные ограничения.

Объект исследования — процесс ведения товарного каталога интернет-магазина. Предмет исследования — структуры данных, алгоритмы обработки запросов и программные средства автоматизации хранения, изменения и поиска сведений о товарах и категориях. В качестве учебного ассортимента используются канцелярские товары. Сведения не относятся к обследованному предприятию; цены и остатки в демонстрационном наборе условные.

При подготовке работы изучены документация библиотек и варианты хранения данных. Для категорий и товаров определены поля, связи и ограничения, затем описаны действия менеджера и разработаны страницы. Проверки сопоставляют ожидаемый результат с сохранёнными данными: допустимый товар должен появиться в каталоге, повторный артикул должен вызвать отказ, а перезапуск сервера должен сохранить записи. Экономический эффект и скорость работы под нагрузкой в задачу проверки не входили.

Результат работы представлен локальным приложением, исходным кодом, инструкцией запуска и тестами. Веб-страницы и JSON API обращаются к одной базе товаров. Первая глава содержит описание предметной области, требования и выбор технологий. Во второй главе приведены модель данных и устройство приложения. Третья глава посвящена реализации операций и результатам испытаний. В приложении размещены снимки страниц программы.

## 1 Теоретические основы и анализ управления товарным каталогом

### 1.1 Особенности ведения каталога товаров интернет-магазина

В каталоге хранятся записи о товарах. У каждой позиции есть название, артикул, категория, цена, описание и текущее количество. Менеджер видит название в списке и использует его при поиске. Названия могут повторяться. Например, две ручки с одинаковым кратким названием могут различаться цветом и толщиной линии. Чтобы вести их отдельно, каждой позиции назначается собственный артикул. Повторение артикула при создании другой записи запрещено.

Идентификатор записи создаётся базой и используется в связях и адресах карточек. Артикул задаёт менеджер. Если он исправляет артикул товара, идентификатор остаётся прежним: меняется существующая запись. Уникальность нового артикула проверяется среди остальных товаров.

Категория объединяет товары по назначению. Её название и описание хранятся отдельно, а товар содержит ссылку на соответствующую запись. Если категория переименована, товары продолжают относиться к ней по прежнему идентификатору. Название категории не требуется вручную исправлять у каждой позиции. Для первой версии выбрана одна категория на товар. Это упрощает форму и условия отбора; иерархическая классификация потребовала бы дополнительных правил перемещения и удаления узлов.

Цена указывается в рублях с точностью до копейки. Допустимы ноль и положительные значения. Остаток содержит целое число единиц товара, начиная с нуля. Позиция с нулевым остатком остаётся в каталоге и открывается по своему адресу, но при отборе по наличию не показывается. В карточке хранится только текущее количество. Причины его изменения, приход, списание и резервирование отдельных записей не имеют. При исправлении остатка прежнее число заменяется новым.

Для товара и категории в программе определены модели. Состав входящего запроса проверяется отдельной схемой, а для ответа подготавливаются нужные клиенту поля. В книге Think Python рассмотрены классы для описания пользовательских типов и словари для хранения пар ключ–значение [3, гл. 10, 14]. В проекте класс модели содержит поля записи, а словарь значений формы сохраняет введённый текст при ошибке. Эти объекты используются на разных этапах обработки запроса.

Основной пользователь модуля — менеджер каталога. Он создаёт категории и товары, находит нужные позиции, исправляет или удаляет их. После успешного сохранения открывается карточка либо список. При ошибке форма сохраняет введённые значения и показывает причину отказа, чтобы менеджеру не приходилось заполнять все поля заново.

В рамках каталога запись описывает товарную позицию, а не отдельную физическую единицу. Десять одинаковых ручек представлены одним товаром с количеством 10. Если отличаются признаки, по которым менеджер должен вести отдельный остаток, создаются разные позиции с собственными артикулами. Так, синие и чёрные ручки могут иметь одинаковую цену и находиться в одной категории, но изменяются независимо. Такое толкование определяет, какие данные вводятся в карточку и что означает количество.

Название товара может совпадать с названием другой позиции. Это нужно, например, для одинаково названных товаров в разных упаковках. Их различают по артикулу. Для категорий повтор имени запрещён: «Бумага» и «БУМАГА» считаются одним разделом. Перед сравнением имена категорий приводятся к общей форме. Такой порядок проверок сохраняет отдельные товарные позиции и предотвращает создание нескольких категорий, различающихся только написанием имени.

Сведения в карточке разделены на обязательные и дополнительные. Без названия менеджер не распознает позицию, без артикула не проверит её уникальность, без категории не сможет применить соответствующий отбор. Описание уточняет характеристики и может отсутствовать. Дата создания и дата изменения заполняются программой, поскольку их ручной ввод не нужен для операций каталога. Зафиксированные правила позволяют определить допустимое состояние записи до разработки формы и не зависеть от её внешнего оформления.

### 1.2 Подходы к автоматизации и требования к модулю

При выборе способа ведения каталога рассмотрены электронная таблица, готовая система магазина и отдельный программный модуль. Сравнение касается операций, которые нужны по заданию: редактирования товаров, связи с категориями и проверки ввода. Коммерческие продукты не устанавливались. Стоимость внедрения и время работы менеджера не измерялись. Выбор сделан по тому, какие части программы предстоит разработать и показать в курсовой.

В электронной таблице товары можно записать по строкам, а свойства разместить в столбцах. Для повторных артикулов и связанных категорий понадобятся дополнительные проверки. Таблица подходит для составления исходного перечня, но в ней не разрабатываются предусмотренные заданием веб-формы и обработчики запросов. При использовании готовой системы пришлось бы выбрать продукт и настроить его. В этой работе требуется написать модуль на Python, поэтому выбран вариант самостоятельной разработки.

Для курсовой выбран самостоятельный веб-модуль: в нём можно реализовать и объяснить обработку запросов, проверку данных и запись в базу. Сравнение подходов приведено в таблице 1. Работа с небольшим запускаемым проектом также позволяет разбирать отдельные операции на воспроизводимых примерах [7].

Бизнес-требования задают назначение модуля: вести общий каталог, исправлять цены и остатки, находить нужные позиции и предотвращать недопустимые записи. Пользовательские требования описывают действия менеджера. Функциональные требования определяют, как система выполняет эти действия. Например, менеджеру нужно исправить цену, а система должна проверить введённое значение и сохранить его у выбранного товара. Бизнес-правила отдельно задают уникальность артикула и допустимые значения данных.

Функциональные требования включают создание, просмотр, изменение и удаление товаров и категорий, подробную карточку товара, поиск по названию, фильтрацию категории и цены, признак наличия, сортировку и постраничный вывод. Условия отбора должны сочетаться. Поиск не зависит от регистра русского текста; ценовые границы включают равные значения. Страница списка содержит не более десяти товаров, а ссылки переходов сохраняют выбранные условия.

Для товара обязательна ссылка на существующую категорию. Артикул и нормализованное имя категории должны быть уникальны. Цена допускает нулевое значение, остаток должен быть целым и неотрицательным. Категория с товарами защищена от удаления. После остановки и запуска сервера ранее внесённые записи должны оставаться доступными. При отказе сохранения прежние данные должны сохраняться. Проверка каждого условия включает чтение результата из базы.

Для каждой операции проверяется успешный запрос и причины отказа. При создании товара это повторный артикул, неправильная цена и отсутствующая категория; при редактировании дополнительно проверяется сохранность прежних данных после ошибки. Вводная глава The Fuzzing Book объясняет проверку через сопоставление результата с ожидаемым поведением и отмечает ограниченность отдельных тестовых примеров [10].

Потребность менеджера описывается через его действие: добавить товар, исправить цену или найти позиции категории. При проектировании API для этого действия определяются поля запроса и ответы сервера. В базе задаются ограничения хранения. Например, запрет повторного артикула проверяется перед сохранением; при конфликте API возвращает 409. Ограничение UNIQUE также запрещает повтор на уровне таблицы. При испытании проверяются ответ сервера и состояние записи после отказа.

Для приёмки операции задаются исходное состояние, действие и ожидаемый результат. Перед проверкой удаления занятой категории в базе должны существовать категория и связанный товар. Затем выполняется запрос удаления. Правильный результат включает отказ и сохранение обеих записей. Если проверить только текст сообщения, можно пропустить ошибочное изменение базы. По той же причине проверка редактирования должна читать запись после сохранения, а проверка неуспешного редактирования — сравнивать её с прежними значениями.

Требования к удобству в проекте выражены через конкретные действия. Менеджер должен видеть, какое поле не принято, и иметь возможность исправить его без повторного заполнения формы. При удалении он сначала видит название и артикул объекта. При переходе между страницами сохраняются фильтры. Эти свойства проверяются через ответы HTML и браузерные сценарии. Оценка удовлетворённости пользователей и сравнение времени выполнения операций с другими системами не проводились, поэтому такие показатели не используются как результат работы.

### 1.3 Обоснование выбора технологий

Для разработки используется Python 3.12. На нём написаны обработчики запросов, схемы входных данных и операции каталога. Версии пакетов перечислены в файлах зависимостей. Пакеты устанавливаются в виртуальное окружение проекта. Чтобы повторить запуск, нужны также команды установки и сведения о среде. Подготовка таких сведений и фиксация условий получения результатов рассмотрены в Research Software Engineering with Python [4]. В репозитории команды приведены в README.

FastAPI выбран для обработки HTTP-запросов и предоставления JSON API. Пользовательские страницы формируются сервером с Jinja2. Документация FastAPI описывает передачу объекта запроса, имени шаблона и контекста в TemplateResponse, а также подключение статических файлов [13]. Такая организация подходит для небольшого интерфейса менеджера: после отправки формы сервер проверяет данные и возвращает страницу либо перенаправление. Основные операции не зависят от JavaScript.

Для работы с данными применяется SQLAlchemy, для входных схем — Pydantic. Сессия SQLAlchemy связывает загруженные объекты с транзакцией и предоставляет явные commit и rollback [14]. Строгий режим Pydantic ограничивает неявные преобразования типов [16]. В API количество и идентификатор категории принимаются целыми JSON-числами. HTML передаёт строки, поэтому адаптер формы отдельно разбирает допустимую целочисленную запись, затем применяет ту же схему.

СУБД выбрана с учётом локальной демонстрации. Согласно документации Python, SQLite хранит данные в файле и не требует отдельного серверного процесса [11]. В задании среди источников названа PostgreSQL. Её документация использована для анализа таблиц, ключей и ограничений [12]. При этом цель задания не закрепляет конкретную СУБД, а фактически реализованная версия использует SQLite. Это решение уменьшает число действий при установке на Mac и позволяет создавать отдельные файлы для тестов.

В приложении используются особенности SQLite: проверки typeof и GLOB, параметры подключения и команды PRAGMA. При переходе на PostgreSQL эти места придётся пересмотреть. Затем нужно заново проверить таблицы, ограничения и запросы на выбранной СУБД. В этой работе перенос не выполнялся. Тесты охватывают локальный запуск с SQLite. Допустимое число одновременно работающих менеджеров по этим результатам не установлено.

Тесты базы, API и HTML выполняются через pytest и тестовый HTTP-клиент, действия в браузере — через Playwright [17; 19]. Для локального запуска используется Uvicorn: ему передаются модуль приложения, адрес и порт [20].

HTML-страницы формируются на сервере. Отдельное клиентское приложение и сборщик JavaScript для запуска не нужны. Маршрут получает запрос, вызывает функцию каталога и передаёт результат шаблону. Формы отправляются браузером обычным HTTP-запросом и работают с отключённым JavaScript. Для API тот же результат преобразуется в JSON. Маршруты используют общие операции записи и поиска, но подготавливают ответы каждый в своём формате.

Операции с SQLite выполняются синхронно. На каждый запрос создаётся отдельная сессия SQLAlchemy, которая закрывается после обработки. Общая сессия для всех запросов не используется. Такая схема проверялась при локальной работе с каталогом. Для нескольких менеджеров дополнительно понадобятся испытания одновременной записи: например, попытки создать один артикул и изменить один товар из разных сеансов. При этих испытаниях нужно проверить блокировки, результат сохранения и сообщения об отказе.

Версии библиотек указаны в requirements.txt и requirements-dev.txt. После установки команда pip check проверяет совместимость зависимостей установленных пакетов. Далее запускается pytest, который выполняет запросы и проверяет данные. Для повторения демонстрации нужно получить исходники, создать окружение Python 3.12 и выполнить команды из README. При запуске приложение создаёт файл базы и недостающие таблицы. Сам рабочий файл базы в Git не хранится; после получения проекта его можно заполнить загрузчиком примеров.

## 2 Проектирование модуля управления каталогом

### 2.1 Пользовательские сценарии и функциональная модель

Пользовательские сценарии начинаются с формирования структуры каталога. Менеджер создаёт категорию, вводя название и необязательное описание. Если эквивалентное нормализованное название уже существует, сервер отклоняет запись и возвращает форму. После успешного сохранения категория доступна для выбора при создании товара. При пустом справочнике форма товара предлагает сначала создать категорию, поскольку ссылка на неё обязательна.

Создание товара включает название, артикул, категорию, цену и остаток. Описание допускается не заполнять. После проверки сервер сохраняет запись и открывает карточку с результатом. При редактировании форма содержит текущие значения; сохраняется тот же идентификатор. Если новый артикул занят, изменённый товар не должен частично получить другую цену или название. Соответствующие проверки выполняются до изменения объекта и повторяются ограничением уникальности при записи.

Поиск сочетается с категорией, нижней и верхней границами цены, наличием и сортировкой. Отключённое условие не ограничивает выдачу. Признак наличия означает количество больше нуля, а не положительную цену. При переходе на следующую страницу сохраняются все условия. Пустая выдача отличается от отсутствия данных в новом каталоге: в первом случае предлагается изменить отбор, во втором — создать первые записи. Связь требований и признаков корректности приведена в таблице 2.

Удаление товара разделено на открытие подтверждения и изменение базы. GET показывает сведения и выбор действия; только POST выполняет удаление. Отмена возвращает карточку. Удаление занятой категории вместо подтверждения показывает причину запрета и ссылку на её товары. Сервер проверяет это правило повторно при POST, поскольку состав категории мог измениться после открытия страницы.

Неправильные данные возвращают статус 422, отсутствие объекта — 404, конфликт уникальности или связи — 409. API передаёт ошибку в JSON, веб-интерфейс показывает HTML-страницу с сообщением. Успешное создание через API возвращает 201, удаление — 204 без тела. После сохранения HTML-формы сервер отвечает перенаправлением 303, и браузер открывает результат запросом GET.

Для каждого сценария определяется проверяемый результат. В книге Х. Персиваля функциональный тест описывает поведение программы с точки зрения пользователя; проверки отдельных частей помогают найти место ошибки [6, гл. 4]. В проекте запросы к API и HTML используются для проверки действий с каталогом. Тесты базы проверяют ограничения таблиц. Браузерные сценарии воспроизводят работу с формами и переходы по ссылкам. Для каждого вида проверки сохранены команды запуска или отчёт.

Редактирование товара можно описать как последовательность состояний. Сначала GET загружает существующую запись и заполняет форму. Затем менеджер отправляет изменённые поля. До успешной фиксации экран с новым вводом ещё не означает изменения базы. При ошибке сервер повторно показывает форму со статусом 422 или 409; при успехе выполняет перенаправление на карточку. Благодаря этому различаются введённые значения, сохранённая запись и представление результата, хотя пользователь видит их в одном интерфейсе.

Страница подтверждения открывается по идентификатору товара. Между её открытием и отправкой формы запись может быть изменена или удалена другим запросом. Поэтому обработчик POST заново получает товар из базы. Если его уже нет, сервер возвращает 404. Для категории также повторно проверяется наличие связанных товаров. Запрос GET только показывает страницу: открытие ссылки и её обновление не меняют базу. Удаление выполняется после отправки формы подтверждения.

Отсутствующий объект и неправильный запрос требуют разной реакции. Существующий по формату идентификатор, для которого нет записи, приводит к 404. Отрицательное или слишком большое число не проходит проверку параметра и даёт 422. Аналогично допустимый диапазон цены с пустой выдачей возвращает успешный список, а диапазон с нижней границей выше верхней отклоняется. Такие различия помогают менеджеру понять причину результата и позволяют тестам проверять поведение без разбора произвольного текста страницы.

JSON API предоставляет те же операции без браузерных форм. Например, после создания товара ответ содержит его идентификатор, название категории и цену в согласованном формате. Дальнейшее чтение по этому идентификатору должно вернуть сохранённые значения. Это используется в автоматических сценариях, где результат одной операции становится входными данными следующей. В проекте такой способ работы нужен для проверки программного контракта; подключение внешней учётной системы или действующего магазина не выполнялось.

### 2.2 Проектирование базы данных и ограничений целостности

Модель включает сущности «Категория» и «Товар» со связью один ко многим. Категория имеет первичный ключ id, название, нормализованное название и описание. Товар содержит id, название, его нормализованную копию, артикул, описание, category_id, цену в копейках, количество и даты создания и изменения. Каждая товарная запись ссылается на одну существующую категорию. Логическая структура показана на рисунке 1.

<!-- figure:model -->

Название категории записывается один раз в таблице categories. Товары ссылаются на неё через category_id. При переименовании меняется строка категории, а ссылки товаров сохраняются. В документации PostgreSQL описаны первичные и внешние ключи, а также ограничение уникальности [12]. В приложении эти средства используются в таблицах SQLite, описанных моделями SQLAlchemy. Для связи задано RESTRICT: удалить категорию, на которую ссылается товар, нельзя.

Цена хранится целым числом копеек. Строка рублей проверяется по допустимому формату и преобразуется через Decimal. Принимаются точка и запятая, не более двух знаков после разделителя; лишняя точность отклоняется без скрытого округления. Документация decimal объясняет возможность точного представления десятичных значений в отличие от ряда значений float [11]. При выводе целые копейки снова преобразуются в строку рублей с двумя дробными знаками.

Количество хранится целым числом в диапазоне SQLite. Входная схема отклоняет дробные и логические значения. В таблице ограничение CHECK проверяет тип и неотрицательность. Для артикула и нормализованного имени категории заданы уникальные индексы. Перед записью приложение ищет совпадение и может сразу сообщить, какой артикул занят. Ограничение базы остаётся действующим при записи, в том числе если совпадающие запросы поступили почти одновременно.

Для поиска используется дополнительное нормализованное имя: NFKC, удаление крайних пробелов и casefold. Согласно документации unicodedata, NFKC сочетает совместимостное разложение с канонической композицией [11]. Исходное название сохраняется для отображения. Служебные поля заполняются моделями при записи через приложение. Здесь нормализация означает преобразование Unicode-строки, а не изменение реляционной схемы. Основные поля и правила сведены в таблицу 3.

Пустое описание после удаления крайних пробелов сохраняется как NULL. Даты записываются в UTC без информации о часовом поясе в самом поле SQLite; API добавляет обозначение UTC, а браузер может показывать местное время. Поле остатка содержит текущее число единиц. Отдельных записей о приходе и списании в базе нет.

Каждое ограничение таблицы проверяет определённое условие. NOT NULL требует значение обязательного поля. CHECK проверяет тип и допустимый диапазон. UNIQUE запрещает совпадения артикула и нормализованного имени категории. Внешний ключ требует существующую категорию. Например, положительное число в category_id может быть допустимо по типу, но отсутствовать в таблице categories. Проверка диапазона такое значение пропустит, а внешний ключ отклонит. При прямой записи тесты отдельно проверяют эти случаи.

Наибольшее целое число SQLite равно 2^63 − 1. Поле price_kopecks содержит копейки, поэтому максимальная принимаемая цена в рублях составляет 92233720368547758.07. Строка с окончанием .08 уже выходит за этот предел. До обращения к базе схема сравнивает значение с границей и возвращает ошибку ввода. Это предотвращает переполнение при сохранении. Для количества используется тот же верхний предел целого числа. Количество проверяется напрямую, без пересчёта денежных единиц.

Хранение цены в копейках сохраняет точность сравнения границ: 49,90 рубля превращаются в 4990, а 50 рублей — в 5000. Фильтр может сравнивать целые значения без округления при каждом запросе. Преобразование выполняется до записи через Decimal; строка с тремя дробными знаками отклоняется. Внутреннее поле price_kopecks не принимается из публичного запроса. Клиент передаёт цену в рублях, а сервер сам получает представление хранения и возвращает цену с двумя знаками после разделителя.

При присваивании названия модели обновляется и его нормализованная копия. После переименования поиск использует новую строку, а на странице показывается исходное написание. Прямой SQL не вызывает Python-валидаторы. Если таким запросом поменять только название, служебное поле останется прежним и поиск может вернуть неверный результат. Поэтому операции приложения записывают данные через модели. При добавлении импорта нужно будет также выполнять нормализацию и проверять соответствие обеих строк.

### 2.3 Архитектура приложения и проектирование интерфейса

Компоненты организованы по назначению: database.py создаёт движок и сессии; models.py описывает хранимые сущности; schemas.py проверяет ввод; catalog.py реализует общие операции; маршруты API и страниц адаптируют запросы и ответы. Шаблоны и статические файлы отвечают за представление. Ответственность компонентов приведена в таблице 4, путь запроса — на рисунке 2.

<!-- figure:architecture -->

Общие операции вынесены из обработчиков запросов по принципу разделения прикладной логики и кода взаимодействия [5, гл. 4]. В модуле их реализуют функции catalog.py, работающие с сессией SQLAlchemy. Отдельный слой репозиториев, очередь событий и собственная реализация Unit of Work не используются.

HTML и API вызывают одинаковые функции каталога. Например, проверка занятости категории находится в общей операции, поэтому правило не зависит от того, каким интерфейсом воспользовался менеджер. Для каждого запроса выдаётся собственная сессия, успешная запись подтверждается явно, конфликт целостности сопровождается rollback. Идея атомарной операции обсуждается в книге Персиваля и Грегори [5, гл. 6], а конкретное поведение сессии определяется SQLAlchemy [14].

Интерфейс включает список товаров с фильтрами, карточку, общую форму создания и изменения, подтверждение удаления и страницы категорий. На широком экране меню расположено слева. На узком — сверху, поля формы выстраиваются последовательно. Таблица прокручивается в собственном контейнере. Для полей предусмотрены подписи, для ошибок — заметное сообщение с сохранённым вводом. Основные действия доступны без JavaScript; скрипт дополняет отображение дат местным временем.

Рабочие данные находятся в data/catalog.db. Этот файл исключён из Git; в репозитории хранятся код и генератор примеров. Обновление исходников не заменяет рабочую базу. Для тестов создаются отдельные SQLite-файлы. Выборка записей из базы по ключам рассматривается в учебных материалах Г. Уилсона [7].

Граница между слоями видна на примере ошибки уникальности. Функция каталога сообщает о конфликте через CatalogError и не выбирает HTML-шаблон. Маршрут страницы возвращает форму с введёнными значениями, а обработчик API — JSON с полем detail. Благодаря этому изменение оформления сообщения не требует менять алгоритм поиска дубликата. В обратную сторону шаблон не выполняет запросы записи и не принимает решение, можно ли удалить занятую категорию.

Зависимость get_db создаёт сессию для запроса и закрывает её после использования. Функция каталога выполняет commit, когда запись готова к сохранению. При известном конфликте она делает rollback и возвращает ошибку операции. В тестах зависимость подменяется сессией временной базы. Поэтому тот же обработчик можно вызвать без обращения к рабочему каталогу. Шаблоны получают уже подготовленные данные и не управляют подключением. Для страниц и API применяется одна зависимость FastAPI.

Для списка и формы нужны разные представления одних данных. В списке показываются краткое название, категория, цена и остаток; карточка содержит описание и даты. Форма дополнительно передаёт ограничения длины и допустимого ввода в HTML-атрибутах. Серверная схема остаётся обязательной, поскольку запрос можно отправить без браузера. Шаблоны отвечают за подписи и расположение элементов, а схема определяет, какие значения могут поступить в операцию каталога.

## 3 Разработка и тестирование модуля

### 3.1 Реализация операций с товарами и категориями

Точкой входа служит app/main.py. При запуске lifespan создаёт отсутствующие таблицы. Путь к data/catalog.db вычисляется от папки проекта. Повторная инициализация сохраняет записи, но не выполняет миграцию существующей схемы. Локальный запуск выполняется Uvicorn с адресом 127.0.0.1 и портом 8000; назначение параметров соответствует документации сервера [20]. Локальная работа приложения на macOS дополнительно проверена студентом.

API содержит десять операций: получение списка, создание, чтение одной записи, изменение и удаление для каждой сущности. Создание товара сначала проверяет схему, наличие категории и уникальность артикула. После добавления объекта выполняется commit, затем обновление его состояния для ответа. Артикул приводится к верхнему регистру. При изменении проверяется существующая запись, новая категория и артикул, после чего заменяются редактируемые поля.

При редактировании сначала проверяются новые значения, затем они присваиваются товару. Если артикул уже занят, функция возвращает отказ до изменения цены и названия. При конфликте во время записи обработчик IntegrityError выполняет rollback и возвращает 409. Порядок восстановления сессии после неудачной записи описан в SQLAlchemy [14]. Тест отправляет конфликтный запрос, сравнивает товар с прежними значениями, а затем выполняет допустимое обновление. Так проверяется продолжение работы после отказа.

Перед удалением категории общая функция проверяет, есть ли в ней товары. Дополнительно удаление занятой категории запрещено внешним ключом с RESTRICT. Удаление отдельного товара сохраняет категорию. Поле updated_at обновляется средствами модели при изменении записи. Маршруты возвращают результат в JSON или HTML. Для PUT требуется полный набор обязательных редактируемых полей; частичное обновление не реализовано.

HTML-форма возвращает введённые значения при 422 и конфликте 409. После успеха браузер получает перенаправление 303 на карточку либо список. RFC 9110 определяет назначение 303 See Other как переход к ресурсу, представляющему результат исходного запроса [18, п. 15.4.4]. Следующий просмотр выполняется GET, поэтому обновление карточки не повторяет сохранение. Открытие страницы подтверждения также не удаляет объект.

Поля HTML-формы поступают на сервер строками. Схема количества и категории принимает целые числа, поэтому адаптер формы предварительно разбирает строковую запись. Допускаются только десятичные цифры подходящей длины. Полученное число передаётся Pydantic для проверки диапазона [16]. Запросы JSON проходят строгую проверку типов без этого адаптера. Сервер проверяет ввод при любом способе отправки, в том числе если запрос составлен вручную и ограничения HTML обойдены.

Обработка цены начинается с удаления крайних пробелов и проверки строки регулярным выражением. Допускаются цифры и один десятичный разделитель с одной или двумя последующими цифрами. После замены запятой точкой создаётся Decimal, проверяется предел и вычисляется целое число копеек. Поэтому значения «49», «49.9» и «49,90» приводятся к согласованному формату, а отрицательная цена, экспоненциальная запись и NaN отклоняются. Проверка формата выполняется раньше обращения к базе.

В JSON поля quantity и category_id должны содержать целые числа. Строка «1», дробное число 1.0 и логическое true отклоняются. Адаптер HTML принимает строку из 1–19 десятичных цифр, преобразует её в число и передаёт схеме Pydantic для проверки диапазона. Перед преобразованием создаётся копия словаря. Исходный словарь сохраняет текст полей для повторного вывода формы при ошибке, включая строку, которую не удалось разобрать.

Схемы входа запрещают лишние поля. Клиент не может задать id, name_normalized или внутреннюю цену в копейках вместе с публичными полями товара. Это проверяется до изменения модели. При PUT обязательные поля передаются полностью, поэтому запрос только с новым названием отклоняется. Внутри операции редактирования текущий идентификатор исключается из поиска дубликата артикула: сохранение своего прежнего артикула допустимо, совпадение с другой записью — конфликт.

Функция _commit перехватывает IntegrityError и сначала выполняет rollback. Затем по сообщению SQLite определяется известный конфликт: повтор имени категории, занятый артикул или нарушение связи. В этих случаях возвращается ошибка каталога со статусом 409. Если причина не распознана, исключение передаётся дальше. При отладке остаются исходные сведения об ошибке. Такой порядок даёт возможность отдельно проверить ожидаемые отказы ввода и обнаружить неизвестное нарушение ограничения.

### 3.2 Реализация поиска, фильтрации и веб-интерфейса

Отбор выполняет общая функция list_products. Поиск сравнивает нормализованную строку с нормализованным названием товара. Символы процента и подчёркивания экранируются как буквальный ввод для LIKE. К запросу добавляются выбранные ограничения категории, нижней и верхней цены и количества больше нуля. До выборки проверяется корректность диапазона; минимальная цена не может превышать максимальную.

Сортировка выбирается из фиксированного перечня: название по возрастанию и убыванию, цена по возрастанию и убыванию, недавнее изменение. При равных значениях используется идентификатор, чтобы порядок оставался однозначным. В list_products каждому варианту сортировки соответствует выражение SQLAlchemy; вторым условием задан Product.id. Тесты проверяют порядок при равных значениях основного поля.

Пагинация использует два результата: общее количество подходящих записей и ограниченную страницу данных. Размер страницы равен десяти, смещение определяется номером страницы. Форма фильтрации использует GET, поэтому параметры остаются в адресе. Ссылки переходов сохраняют эти параметры и изменяют только страницу. Ошибочный запрос получает понятный HTML; пустая выдача остаётся успешным результатом, если условия допустимы.

Jinja2 использует общий базовый шаблон с навигацией и отдельные шаблоны списка, карточки, форм и подтверждений. Пользовательские значения передаются через контекст, как описано в документации FastAPI [13]. Включённое окружением шаблонов автоматическое экранирование обрабатывает HTML-символы; пользовательский текст не помечается safe. Документация Jinja описывает исключения из экранирования и зависимость поведения от настройки [15]. Тесты с введёнными тегами проверяют вывод текста без исполнения разметки.

Для демонстрации большого списка подготовлены 1200 синтетических товаров в 12 категориях. На каждую приходится 100 записей. Отличаются типы, варианты, цены и остатки; 133 товара имеют нулевое количество. Цена находится в диапазоне 19,00–346,10 рубля. Генератор не описывает прайс-лист действующего поставщика. Записи помечены как демонстрационные и имеют стабильные артикулы.

Перед записью в существующую базу загрузчик создаёт резервную копию методом SQLite backup [11]. Метод читает базу через соединение SQLite и учитывает зафиксированные данные. После создания копии начинается транзакция загрузки. Занятые артикулы пропускаются, описания существующих категорий остаются прежними. Повторный запуск сохраняет исправленные менеджером цену и название. Набор имеет постоянные артикулы, поэтому его можно загрузить на другом компьютере и повторить поиск по тем же позициям.

Составной отбор строится как пересечение условий. Например, для запроса «РУЧКА», выбранной категории, диапазона 49,90–100,00 рубля и включённого наличия товар должен удовлетворять всем четырём ограничениям. В тестовом наборе синяя ручка за 49,90 и гелевая за 100,00 попадают в результат, а красная за 99,00 с нулевым остатком исключается. Пример одновременно проверяет регистр поиска, включение граничных цен и независимость наличия от цены.

Для подсчёта и выборки страницы используется один список условий. Сначала считается общее число подходящих строк, затем выполняется запрос с LIMIT 10 и OFFSET. Для первой страницы смещение равно нулю, для второй — десяти. При 13 результатах страницы содержат 10 и 3 записи. Число страниц вычисляется с округлением вверх; даже при пустом результате интерфейс сохраняет первую страницу. Если запрошен номер за пределами выдачи, данные не подменяются результатами другой страницы.

Категория загружается вместе с товаром через joinedload. В строке списка нужно её название, поэтому запрос получает связанные данные до передачи объектов шаблону. Шаблон обращается к product.category.name и не запускает отдельную операцию загрузки для каждой строки. В этом проекте joinedload выбран по составу данных страницы. Сравнение скорости запросов с другими способами загрузки не выполнялось. В автоматическом тесте проверяется, что список содержит правильные названия категорий.

Ссылки пагинации формируются через urlencode из действующих параметров с заменой номера страницы. Это сохраняет поисковую строку, категорию и границы цены при переходе. Новая отправка формы фильтров не переносит прежний номер страницы, поэтому поиск начинается заново. Параметры удобно воспроизвести из адреса, однако адрес не является снимком данных: если каталог изменится, тот же запрос может вернуть другой состав позиций. Устойчивый порядок при равных значениях уменьшает неоднозначность выдачи, но не фиксирует состояние базы между запросами.

### 3.3 Тестирование, анализ результатов и ограничения решения

Проверка выполнена 21.10.2026 в облачной Linux-среде на Python 3.12. Автоматические тесты получают отдельные временные SQLite-файлы. Фикстуры создают движок, схему и сессию, а тестовый клиент подменяет зависимость доступа к базе. Такой способ организации согласуется с механизмом фикстур pytest [17]. Рабочий каталог не используется для записи тестовых примеров. Его демонстрационное наполнение выполнено отдельно загрузчиком после резервного копирования.

Всего пройдено 154 теста: 35 проверок базы, 81 API, 31 HTML и 7 загрузчика. Проверяются операции, уникальность, типы и границы чисел, обязательность связи, поиск русского текста, сочетания фильтров, сортировка, пагинация и отказ без частичного изменения. Для загрузчика дополнительно проверены повторное применение, сохранение собственных записей, откат при искусственном сбое и резервная копия с зафиксированными данными WAL.

При запуске получено одно предупреждение Starlette об устаревающем использовании HTTPX в TestClient. Все тесты завершились успешно. Набор можно повторно запускать после изменения кода для проверки перечисленных сценариев; такую роль автоматических тестов рассматривает Software Engineering at Google [8, гл. 11].

Дополнительно выполнены 14 сценариев в Chromium 154.0.8037.57 при размерах экрана 1440 × 1000 и 390 × 844. Через Playwright проверены формы, сообщение о неправильной цене с сохранением ввода, совместный отбор, пагинация, защита категории, отмена и подтверждение удаления. Также проверена форма при отключённом JavaScript. Использован синхронный интерфейс автоматизации, соответствующий документации Playwright для Python [19].

Браузерный прогон выявил расширение мобильной страницы скрытой подписью таблицы. Ошибка воспроизведена на узком экране; позиционирование подписи ограничено прокручиваемым контейнером. Повторная проверка сравнила ширину документа с шириной окна. Проверка выполнена по схеме воспроизведения и локализации отказа, описанной в The Debugging Book [9]. Также исправлено выравнивание последнего столбца и добавлены проверки слишком больших идентификаторов адресов.

На этом наборе в Chromium выполнены ещё шесть сценариев большого каталога: количество записей API, переход по страницам, последняя страница, совместные фильтры, счётчики категорий и мобильная ширина. Список из 1200 товаров образует 120 страниц; в каждой категории отображается 100 товаров. Итоги сведены в таблицу 5. integrity_check вернул ok, foreign_key_check — отсутствие ошибок; повторная загрузка добавила ноль записей.

Проверка сохранности включает повторное открытие файловой базы другим процессом и отдельный HTTP-прогон с перезапуском на этапе разработки API. В приложении А показаны общий список (рисунок А.1), форма редактирования (рисунок А.2), ошибка цены (рисунок А.3) и запрет удаления занятой категории (рисунок А.4). Снимки фиксируют реальные страницы: часть относится к раннему сценарию изменения одного товара, часть — к большому набору. Все изображения относятся к учебному каталогу. Подход к документированию условий и происхождения результата рассматривается в работе Ирвинга и соавторов [4].

Проверки относятся к локальной работе с каталогом. Нагрузочное тестирование, одновременное редактирование несколькими менеджерами и перенос на PostgreSQL не проводились. Для многопользовательской эксплуатации потребуются авторизация, журнал изменений, миграции схемы и проверка конкурирующих записей.

Проверки хранения и проверки API подтверждают разные части одного правила. Тест базы может выполнить прямую запись недопустимого значения и получить отказ ограничения SQLite. Тест API проверяет, что неправильный запрос вернул 422 или 409 и не изменил каталог. Если использовать только API, ограничение базы могло бы отсутствовать и оставаться незамеченным благодаря входной схеме. Если проверять только базу, могли бы сохраниться неверный код ответа и потеря введённых значений формы.

Граничные примеры выбираются по правилам конкретных полей. Для названия проверяются пустая строка, пробелы и превышение допустимой длины; для цены — ноль, лишняя точность, запрещённые представления и предел целого SQLite. Для количества отдельно рассматриваются отрицательное, дробное, логическое и слишком большое значения. Поиск проверяется на русском регистре и буквальных символах процента, подчёркивания и косой черты. Эти случаи связаны с реализацией схем и запроса, а не со случайным набором товаров.

Тест повторного артикула сохраняет прежние значения товара, отправляет конфликтное обновление и заново читает запись. После отказа поля должны совпадать с исходными. Далее отправляется допустимое обновление и проверяется его результат. В другом сценарии меняется category_id товара. Ответ должен содержать идентификатор и название новой категории. Если прежняя категория стала пустой, её можно удалить. Проверка охватывает изменение существующей связи и сохранение самого товара.

Для загрузчика искусственный сбой вызывается при выполнении INSERT товара. После исключения проверяется отсутствие и товаров, и категорий, добавленных неудачной транзакцией. Отдельный тест подменяет создание резервной копии ошибкой и подтверждает, что загрузка не начинается. В WAL-сценарии запись сначала фиксируется в журнале открытой базы, затем читается из резервной копии. Так проверяются разные отказы: откат незавершённой загрузки, запрет записи без копии и включение уже зафиксированных данных.

В тесте повторной загрузки сначала создаются собственный товар и категория с описанием. Затем добавляется демонстрационный набор, и у одной его позиции изменяются цена и название. После второго запуска загрузчика тест читает эти записи. Пользовательские значения должны сохраниться, а артикулы не должны повториться. Также проверяется число добавленных и пропущенных товаров. Сравнение полей обнаруживает перезапись данных даже в случае, когда общее количество записей осталось правильным.

Если артикул пользовательского товара совпал с артикулом набора, загрузчик пропускает эту позицию. Для проверки заранее создаётся товар DEMO-01-01-01 в другой категории. После загрузки ожидаются 1199 новых товаров и один пропуск. У исходной записи проверяются прежнее название и категория. Загрузчик использует артикул для определения занятой позиции и не пытается установить её происхождение по описанию. Это правило сохраняет пользовательскую запись при повторном наполнении каталога.

После запуска отдельно проверяется готовность обычного сервера командой scripts.check_ready. Проверка открывает главную страницу с перенаправлением, списки и формы, получает локальные CSS и JavaScript, читает health и списки API. Затем по OpenAPI проверяется наличие десяти операций каталога. Ожидание ответа 200 дополняется проверкой содержания: заголовка HTML, формата JSON и необходимых полей списка. Поэтому случайно запущенный на том же порту другой сервер не удовлетворит всем условиям только благодаря доступности адреса.

Команда scripts.check_ready читает структуру рабочей базы без добавления товаров. Через SQLAlchemy запрашиваются имена таблиц, столбцы товара и внешний ключ категории. Отдельно проверяется включение PRAGMA foreign_keys для соединения. Ответ health сообщает о работе HTTP-процесса и сам не обращается к каталогу. Поэтому проверка схемы нужна дополнительно: запущенный сервер может отвечать на health при неверной структуре базы. Команду можно выполнять после запуска и обновления исходников; рабочие записи она не меняет.

Результат тестов относится к версии исходников и зависимостей, использованных при запуске. После изменения схемы или перехода на другую СУБД проверки нужно повторить. В документации указаны даты pytest, HTTP-проверок с перезапуском и браузерных отчётов. Снимки от 21.10.2026 показывают интерфейс того дня. После изменения надписей они сохраняются как часть прежнего отчёта. Актуальный вид страницы проверяется новым запуском браузера и новым снимком.

## Заключение

Разработан локальный модуль управления каталогом товаров на Python 3.12, FastAPI и SQLite. Через веб-интерфейс и JSON API можно создавать, просматривать, изменять и удалять товары и категории, искать позиции и применять фильтры. Для демонстрации используется ассортимент канцелярских товаров.

Для реализации выбран самостоятельный модуль, поскольку задание требует разработки и объяснения собственного кода. SQLite позволяет запускать его без отдельного сервера базы данных и создавать временные базы для тестов. Документация PostgreSQL использована при сравнении решений; переноса приложения на эту СУБД не было.

В базе созданы таблицы категорий и товаров со связью один ко многим. Товар ссылается на категорию по идентификатору. Цена хранится целыми копейками, количество проверяется как неотрицательное целое число. Нормализованная копия названия используется при поиске и сравнении имён категорий. Входящие запросы проверяются схемами. Запись и поиск выполняют функции каталога, которые вызываются из маршрутов HTML и API.

Реализованы десять операций API, карточки и формы, подтверждение удаления, обработка ошибок с сохранением ввода. Поиск сочетается с категорией, включительными ценовыми границами и наличием. Фиксированный перечень сортировок и дополнительный порядок по идентификатору делают выборку однозначной. Пагинация ограничивает страницу десятью записями и сохраняет условия при переходах. Основные формы работают без JavaScript, а локальное отображение дат дополняется скриптом.

Для демонстрации подготовлены 1200 товаров в 12 категориях. Перед загрузкой в существующую базу создаётся резервная копия, затем недостающие записи добавляются одной транзакцией. Повторный запуск пропускает занятые артикулы и сохраняет пользовательские изменения. Проверки целостности SQLite нарушений не выявили.

Пройдены 154 автоматических теста. В Chromium выполнены 14 сценариев интерфейса и 6 сценариев большого каталога. При проверке на узком экране обнаружено расширение страницы; также найдено неправильное выравнивание столбца. Обе ошибки исправлены и проверены повторно. Команды запуска, условия и отчёты сохранены в репозитории. Одновременная работа нескольких менеджеров и нагрузка в эти испытания не входили.

Модуль выполняет предусмотренные заданием операции с каталогом в локальной среде. Перед использованием несколькими менеджерами нужно добавить авторизацию и историю изменений, подготовить миграции и проверить одновременную запись. Для учебной демонстрации подготовлены исходники, инструкция запуска, демонстрационные данные и материалы защиты.
