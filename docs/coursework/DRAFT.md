## Введение — рабочая основа

Каталог товаров объединяет сведения, необходимые для управления ассортиментом: названия, артикулы, принадлежность к категориям, цены и текущие остатки. В этой работе рассматривается локальный модуль для менеджера учебного интернет-магазина канцелярских товаров. Отдельное внимание уделено проверке вводимых данных и согласованности связей между товаром и категорией. Анализ распространённости проблем и общих тенденций электронной торговли должен быть дополнен изученной научной литературой; количественные сведения здесь не заявляются.

Цель работы — разработать и проверить модуль управления каталогом, позволяющий создавать, просматривать, изменять и удалять сведения о товарах и категориях, находить товары и отбирать их по заданным условиям.

Объект исследования — процесс ведения товарного каталога интернет-магазина. Предмет исследования — структуры данных, методы обработки запросов и программные средства автоматизации хранения, изменения и поиска сведений о товарах и категориях.

Для достижения цели определены задачи: сформировать требования к модулю; выбрать инструменты разработки; спроектировать структуру данных и пользовательские сценарии; реализовать серверные операции и веб-интерфейс; проверить положительные и отрицательные сценарии; описать результаты и ограничения.

Практический результат — приложение на Python с FastAPI, Jinja2, SQLAlchemy и SQLite. Оно предоставляет HTML-страницы и JSON API с общими операциями каталога. При работе использованы моделирование данных и сценариев, программирование и функциональное тестирование. Материалы записки организуются в три главы: теоретический анализ, проектирование, реализация и проверка.

Этот фрагмент введения нужно развить до требуемого объёма после подготовки главы 1. Он не содержит утверждения о внедрении, экономическом эффекте или научной новизне.

## 1 Теоретические основы и анализ управления товарным каталогом

### 1.1 Особенности ведения каталога товаров интернет-магазина

Материал для разработки параграфа: разделить понятия товара, артикула, категории, цены и остатка; описать роль менеджера и отличие каталога от заказа и движения запасов. В этом проекте остаток — текущее целое количество единиц, которое менеджер изменяет вручную. Журнал приходов, списаний и резервирования не ведётся. Канцелярские товары выбраны как учебный ассортимент; обследование действующей организации не проводилось.

Для теоретических определений необходимо подобрать и изучить научные источники. Не приписывать учебному примеру данные реального предприятия.

### 1.2 Подходы к автоматизации и требования к модулю

Выполнить собственное сравнение таблицы, готовой системы управления магазином и отдельного веб-модуля по одинаковым критериям: проверка данных, связи категорий, поиск, сложность установки и возможность изменения кода. Оценки трудозатрат и скорости допустимы только при наличии измерений. Согласованные требования и границы первой версии уже зафиксированы в [PLAN.md](../PLAN.md).

### 1.3 Обоснование выбора технологий

Для проекта выбран Python 3.12. FastAPI принимает HTTP-запросы и предоставляет документацию JSON API. HTML формируется на сервере с Jinja2: обработчик передаёт объект запроса, имя шаблона и словарь данных в TemplateResponse [T1]. Это позволяет использовать обычные формы без отдельного приложения в браузере.

Для доступа к данным применён SQLAlchemy. Сессия связывает объекты и операции с базой; завершение транзакции выполняется явно [T2]. SQLite выбрана проектным решением для локальной демонстрации: отдельный сервер базы не требуется. Это решение не подтверждает пригодность для произвольной нагрузки. Зависимости закреплены в requirements-файлах и проверены в Python 3.12.

Pydantic используется для входных схем. Строгая проверка отдельных полей позволяет отвергать данные неподходящего типа вместо их неявного преобразования [T5]. В проекте это относится к JSON-полям количества и идентификатора категории. HTML-форма отправляет строки; адаптер формы переводит допустимую целочисленную запись в число до проверки той же схемой.

## 2 Проектирование модуля управления каталогом

### 2.1 Пользовательские сценарии и функциональная модель

Основной пользователь — менеджер каталога. Он создаёт категорию, добавляет относящийся к ней товар, проверяет карточку, находит товар по названию, меняет цену и остаток. При удалении открывается подтверждение. Если категория содержит товары, интерфейс объясняет запрет и предлагает открыть их список.

Поиск сочетается с выбором категории, нижней и верхней границами цены, признаком наличия и сортировкой. Наличие означает строго положительный остаток. Границы цены включаются в результат. Список разделён на страницы по десять записей. Параметры отбора сохраняются при переходе по страницам. Сценарии и их соответствие требованиям раскрыты в [DESIGN.md](../DESIGN.md).

### 2.2 Проектирование базы данных и ограничений целостности

Выделены сущности «Категория» и «Товар» со связью один ко многим. Категория имеет идентификатор, название и необязательное описание. Товар содержит идентификатор, название, артикул, описание, идентификатор категории, цену, остаток, время создания и изменения. Товар обязательно связан с существующей категорией; удаление занятой категории запрещено внешним ключом RESTRICT и операцией каталога.

Цена хранится целым числом копеек. Входная строка рублей разбирается через Decimal: принимаются запятая или точка и до двух дробных знаков. Значения с большей точностью не округляются автоматически, а отклоняются. При выводе цена снова представляется строкой рублей с двумя знаками. Так точность денежного значения не зависит от двоичного float.

Остаток — неотрицательное целое в диапазоне SQLite. На уровне входных схем и моделей отклоняются дробные, логические и недопустимо большие значения. CHECK-ограничения SQLite дополнительно защищают обязательные свойства при прямой записи в базу. Уникальность артикула и нормализованного названия категории обеспечивается базой и предварительными проверками.

Для поиска используется дополнительное нормализованное название: NFKC, удаление крайних пробелов и casefold. В документации Python NFKC определена как совместимостное разложение с последующей канонической композицией [T4]. Проектная последовательность преобразований и поиск русских названий проверены тестами. Оригинальное название сохраняется для отображения. Полный словарь полей и ER-схема находятся в DESIGN.md.

### 2.3 Архитектура и пользовательский интерфейс

Компоненты организованы по назначению: database.py создаёт движок и сессии; models.py описывает таблицы и ограничения; schemas.py проверяет входные данные; catalog.py реализует операции; routers/api.py и routers/pages.py адаптируют эти операции к JSON и HTML. Шаблоны отвечают за представление, локальные CSS — за оформление. Небольшой JavaScript переводит UTC-даты в местное время браузера.

Общие операции предотвращают расхождение правил между интерфейсом и API. Например, запрет удаления занятой категории действует в обоих вариантах обращения. Каждый запрос получает собственную сессию. Запись завершается commit; при известных конфликтах целостности выполняется rollback [T2]. Схема компонентов подготовлена в DESIGN.md.

На широком экране меню расположено слева, фильтры — над таблицей. На узком экране меню переходит наверх, поля располагаются последовательно. Широкая таблица прокручивается внутри своего контейнера. Формы сопровождаются видимыми подписями и подсказками, сообщения об ошибках сохраняют введённый текст. Удаление отделено от обычного просмотра.

## 3 Разработка и тестирование модуля

### 3.1 Реализация операций с товарами и категориями

Входной точкой служит app/main.py. При запуске lifespan создаёт отсутствующие таблицы. Путь к файлу базы вычисляется от папки проекта, поэтому не зависит от текущей папки терминала. Повторная инициализация не удаляет записи; автоматического изменения существующей схемы не предусмотрено.

JSON API содержит десять операций: получение списка, создание, получение одной записи, изменение и удаление для товаров и категорий. При создании возвращается статус 201, при успешном удалении — 204 без тела. Отсутствующая запись даёт 404, конфликт уникальности или попытка удалить занятую категорию — 409, неправильный ввод — 422. PUT требует все обязательные редактируемые поля. Примеры запросов и ответов сохранены в STAGE_5.md.

Создание товара выполняется после проверки его полей, существования категории и уникальности артикула. При редактировании эти проверки выполняются до изменения сохранённого объекта. Регистр артикула приводится к верхнему. Если при записи всё же возникает конфликт ограничения базы, транзакция откатывается; другие записи не должны изменяться.

На стороне страниц успешный POST завершается ответом 303 и адресом результата. Затем браузер получает карточку или список отдельным GET. Такая схема согласуется с назначением 303 See Other для перехода после POST к отдельно доступному ресурсу [T6]. Открытие страницы подтверждения через GET не меняет данные.

### 3.2 Реализация поиска, фильтрации и веб-интерфейса

Отбор товаров реализован в общей функции list_products. К запросу добавляются только выбранные условия. Строка поиска сравнивается с нормализованным названием; символы `%` и `_` экранируются как буквальный ввод, а не шаблон SQL LIKE. Условия категории, цены и остатка применяются совместно. Порядок сортировки выбирается из фиксированного перечня, а идентификатор используется для однозначного порядка при равных значениях.

Количество найденных записей вычисляется отдельным запросом. Для страницы применяются limit и offset с размером десять записей. Форма поиска использует GET, поэтому её состояние видно в адресе. При ошибочном диапазоне цены возвращается HTML с кодом 422 и заполненными полями. Отсутствие результатов показано отдельным состоянием.

Jinja2 использует общий базовый шаблон с навигацией и отдельные шаблоны списка, карточки, форм и подтверждений. При включённом автоматическом экранировании Jinja обрабатывает переменные, кроме специально помеченных безопасными значений [T3]. В проекте пользовательский текст не получает такую отметку. Тесты проверяют, что введённые теги выводятся как текст. Основные сценарии форм работают при отключённом JavaScript.

Иллюстрации для этого параграфа: [список](../figures/01-products-desktop.png), [карточка](../figures/02-product-detail.png), [форма](../figures/03-product-form.png), [совместные фильтры](../figures/05-combined-filters.png), [категории](../figures/06-categories.png). В записке изображения нужно вставить после первого упоминания, назначить общую нумерацию и подписи. Это снимки разных шагов тестового сценария: товар меняется с 49,90 ₽ и 24 шт. до 54,90 ₽ и 18 шт.

### 3.3 Тестирование, результаты и ограничения

Проверка проведена 21.10.2026 в облачной Linux-среде. Автоматические проверки используют отдельный файл SQLite для каждого теста. Всего пройдено 147 тестов: 35 проверок данных, 81 проверка API и 31 проверка HTML. Сохранено одно предупреждение о поддерживаемом устаревающем режиме HTTPX в TestClient. Оно не скрывалось и не привело к отказу проверок.

Дополнительно выполнены 14 сценариев в Chromium 154.0.8037.57 с экранами 1440 × 1000 и 390 × 844. Проверены создание и изменение через формы, валидация цены с сохранением полей, совместные фильтры, пагинация, защита занятой категории, отмена и подтверждение удаления, отсутствие ошибок JavaScript и работа формы без JavaScript. Сохранены девять снимков реальных страниц на учебном ассортименте. Полный перечень — в browser-report.json и STAGE_7.md.

Браузерная проверка выявила расширение мобильной страницы скрытой подписью таблицы. Позиционирование подписи ограничено прокручиваемым контейнером; после исправления ширина документа не превышала ширину экрана в проверенных сценариях списка и формы. Также исправлено выравнивание последнего столбца. Дополнительные тесты проверяют недопустимо большие идентификаторы HTML-адресов.

Сохранность данных подтверждена повторным открытием базы другим процессом и ранее выполненным HTTP-прогоном с перезапуском на этапе 5. Рабочая база не использовалась для демонстрационного наполнения; её контрольная сумма до и после текущих проверок совпала. Пользователь подтвердил запуск предыдущей версии на macOS. Это подтверждение не заменяет отдельной проверки нового интерфейса в Safari.

Полученные результаты подтверждают выполнение согласованных функциональных сценариев. Измерение производительности и нагрузочное тестирование не проводились; оценка ускорения работы менеджера не заявляется. В первой версии отсутствуют авторизация, журнал движений запасов и миграции схемы. Направления развития — роли пользователей, учёт операций с остатками, управляемые миграции и проверка работы при одновременном обращении нескольких менеджеров.

## Заключение — рабочая основа

В ходе проектирования и разработки создан локальный модуль управления товарным каталогом. Реализованы операции с товарами и категориями, просмотр подробной карточки, поиск, комбинированные фильтры, сортировка и пагинация. Разработаны JSON API и веб-интерфейс, использующие общие операции и ограничения.

Целостность данных поддерживается проверкой входных схем, правилами моделей и ограничениями SQLite. Цена хранится в копейках, остаток — целым неотрицательным числом. Категория с товарами защищена от удаления. Проверки выявили и позволили исправить дефекты мобильного отображения; итоговые 147 автоматических тестов и 14 браузерных сценариев прошли.

Приложение пригодно для демонстрации согласованных учебных сценариев. Доказательство работы при промышленной нагрузке, внедрение в организацию и экономический эффект в рамках проекта не получены. Для завершения курсовой необходимо дополнить теоретический анализ, собрать и изучить научные источники, оформить полный документ по шаблонам МФЮА и выполнить установленную вузом проверку.
