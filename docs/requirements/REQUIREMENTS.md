# Технические требования

Тема: «Разработка модуля управления каталогом товаров для интернет-магазина».

Автор: Чемоданов Никита Сергеевич.

Группа: 23ИПо8381 (ИПо-41), 4-й курс.

## Основание и цель разработки

Разработка выполняется по учебному заданию на модуль управления каталогом товаров интернет-магазина. В документе определены задачи модуля, действия менеджера, правила данных и условия приёмки.

Цель разработки — дать менеджеру возможность вести каталог через браузер. В модуле должны сохраняться товары и категории, цены и текущие остатки. Менеджер должен находить нужные позиции и исправлять их данные.

## Границы системы

Модуль должен быть рассчитан на локальную работу одного менеджера. В его состав должны входить товары, категории, цены, текущие остатки и операции с этими данными.

Заказы, оплата, доставка, личные кабинеты покупателей, разграничение прав сотрудников, изображения товаров, иерархия категорий и журнал складских движений в первую версию не включаются. В остатке должно храниться текущее количество единиц товара.

## Бизнес-требования

БТ-1. Модуль должен предоставлять менеджеру общий каталог товаров и категорий. Изменения должны сохраняться и быть доступны при следующем запуске.

БТ-2. Модуль должен давать менеджеру возможность поддерживать актуальные цены и текущие остатки. Менеджер должен иметь возможность изменить эти сведения у существующей товарной позиции.

БТ-3. Модуль должен предоставлять отбор позиций по названию, категории, цене и наличию, чтобы менеджер мог найти товары для просмотра и изменения.

БТ-4. Модуль должен предотвращать появление повторных артикулов, недопустимых цен и остатков, а также потерю связи товара с категорией.

## Пользовательские требования

### ПТ-1. Работа менеджера с товарами

ПТ-1.1. Менеджер должен видеть ассортимент в виде списка с основными сведениями о каждой позиции.

ПТ-1.2. Менеджер должен получать подробные сведения о выбранном товаре в отдельной карточке.

ПТ-1.3. Менеджер должен иметь возможность вносить в каталог новые товарные позиции.

ПТ-1.4. Менеджер должен иметь возможность исправлять сведения о товаре, его цену, остаток и принадлежность к категории.

ПТ-1.5. Менеджер должен иметь возможность удалять ненужную товарную позицию с подтверждением действия.

### ПТ-2. Работа менеджера с категориями

ПТ-2.1. Менеджер должен видеть перечень категорий и количество относящихся к ним товаров.

ПТ-2.2. Менеджер должен иметь возможность добавлять категории для организации ассортимента.

ПТ-2.3. Менеджер должен иметь возможность переименовывать категории и изменять их описание.

ПТ-2.4. Менеджер должен иметь возможность открыть товары определённой категории.

ПТ-2.5. Менеджер должен иметь возможность удалить категорию, которая больше не используется.

### ПТ-3. Поиск нужных позиций

ПТ-3.1. Менеджер должен находить товары по фрагменту названия независимо от регистра русских букв.

ПТ-3.2. Менеджер должен отбирать товары по категории и требуемому диапазону цены.

ПТ-3.3. Менеджер должен иметь возможность отдельно просмотреть товары, имеющиеся в наличии.

ПТ-3.4. Менеджер должен иметь возможность сочетать несколько условий отбора.

ПТ-3.5. Менеджер должен иметь возможность убрать выбранные условия и вернуться к полному списку.

### ПТ-4. Просмотр больших списков

ПТ-4.1. Менеджер должен иметь возможность упорядочивать товары по названию и цене в обоих направлениях.

ПТ-4.2. Менеджер должен иметь возможность просматривать недавно изменённые позиции в начале списка.

ПТ-4.3. Менеджер должен просматривать результаты небольшими страницами и видеть общее число найденных товаров.

ПТ-4.4. Менеджер должен иметь возможность продолжать просмотр на следующей странице без повторного задания условий.

### ПТ-5. Контроль результата действий

ПТ-5.1. Менеджер должен получать подтверждение успешного изменения каталога.

ПТ-5.2. Менеджер должен понимать причину отказа и исправлять ввод без повторного заполнения корректных полей.

ПТ-5.3. Менеджер должен иметь возможность отказаться от удаления до его выполнения.

ПТ-5.4. Менеджер должен получать объяснение, если удаление категории запрещено из-за связанных товаров.

## Функциональные требования

ФТ-1. Система должна формировать список товаров с названием, артикулом, категорией, ценой и остатком. При пустом каталоге система должна сообщать об отсутствии записей и предлагать добавление первой позиции.

ФТ-2. Система должна открывать карточку выбранного товара с основными сведениями, описанием и датами создания и изменения. Если товар не существует, система должна сообщать об этом без изменения данных.

ФТ-3. Система должна принимать сведения о новом товаре, проверять обязательные значения и правила данных, после успешной проверки сохранять товар и предоставлять доступ к его карточке.

ФТ-4. Система должна загружать сведения о существующем товаре в форму редактирования и сохранять допустимые изменения в той же записи. При отказе прежние данные должны оставаться доступными.

ФТ-5. Система должна запрашивать подтверждение удаления с указанием удаляемого товара. Отмена должна сохранять запись; подтверждение должно удалять только выбранный товар и возвращать менеджера к списку.

ФТ-6. Система должна формировать список категорий с названиями, описаниями и количеством товаров. Из этого списка должен быть доступен переход к товарам выбранной категории.

ФТ-7. Система должна создавать категорию после проверки заполнения названия и отсутствия эквивалентного имени. Ошибка не должна приводить к созданию дополнительной записи.

ФТ-8. Система должна изменять название и описание категории, сохраняя её связь с товарами. Новое название должно отображаться при последующем просмотре связанных товаров.

ФТ-9. Система должна перед удалением категории проверять, используются ли её данные товарами. Занятую категорию удалять нельзя; система должна объяснять причину и предоставлять переход к связанным товарам.

ФТ-10. Система должна находить товары по вхождению введённого фрагмента в название без учёта регистра. Введённые символы должны рассматриваться как текст поиска, а не как команды или специальные шаблоны.

ФТ-11. Система должна применять выбранные условия поиска, категории, цены и наличия совместно. При отсутствии подходящих товаров должна выводиться пустая выдача с возможностью изменить или сбросить условия.

ФТ-12. Система должна упорядочивать результаты по названию или цене по возрастанию и убыванию, а также по времени изменения от новых к старым. При равных значениях порядок должен оставаться однозначным.

ФТ-13. Система должна выводить до 10 товаров на странице, показывать число результатов и текущую страницу. Переходы должны сохранять условия отбора и сортировки; новый поиск должен начинаться с первой страницы.

ФТ-14. Система должна проверять данные до сохранения, сообщать об успешном действии либо причине отказа и сохранять введённые значения при ошибке формы. Повторный просмотр результата сохранения не должен заново выполнять то же изменение.

ФТ-15. Система должна сохранять зафиксированные сведения между сеансами работы. Повторный запуск должен предоставлять доступ к ранее внесённым товарам и категориям без повторного ввода данных.

## Атрибуты данных

Атрибуты задаются на уровне предметной области. Названия полей хранения, технические ключи и способы представления значений должны определяться при проектировании.

### Сущность «Категория»

| Атрибут | Тип и обязательность | Назначение и правила |
|---|---|---|
| Идентификатор категории | Идентификатор; обязательный, системный | Однозначно определяет категорию и сохраняется при её переименовании. |
| Название категории | Строка; обязательный | Обозначает группу товаров. Должно быть непустым и отличаться от названий других категорий. |
| Описание категории | Текст; необязательный | Поясняет, какие товары относятся к категории. |

### Сущность «Товар»

| Атрибут | Тип и обязательность | Назначение и правила |
|---|---|---|
| Идентификатор товара | Идентификатор; обязательный, системный | Однозначно определяет товарную запись и сохраняется при её изменении. |
| Название товара | Строка; обязательный | Используется для распознавания товара и поиска. Совпадения названий допустимы. |
| Артикул | Строка; обязательный | Уникальное обозначение позиции ассортимента. |
| Категория товара | Связь с категорией; обязательный | Относит товар к одной существующей категории. |
| Цена | Денежное значение; обязательный | Задаётся в рублях с точностью до копейки и не может быть отрицательной. |
| Остаток | Целое число; обязательный | Количество доступных единиц товара, не меньшее нуля. |
| Описание товара | Текст; необязательный | Содержит дополнительные характеристики позиции. |
| Дата создания | Дата и время; обязательный, системный | Фиксирует первоначальное внесение товара. Вручную не редактируется. |
| Дата изменения | Дата и время; обязательный, системный | Фиксирует последнее изменение сведений. Вручную не редактируется. |

## Бизнес-правила

БП-1. Один товар должен относиться ровно к одной категории. Категория может существовать без товаров.

БП-2. Категория с товарами не должна удаляться. До её удаления товары необходимо перенести в другую категорию либо удалить отдельными действиями.

БП-3. Артикулы товаров должны быть уникальны без учёта регистра латинских букв. Изменение регистра не должно позволять создать дубликат.

БП-4. Имена категорий должны сравниваться без учёта регистра и пробелов по краям. Такие различия не должны создавать отдельную категорию.

БП-5. Название товара не должно использоваться как единственный признак уникальности: разные позиции могут иметь одинаковое название и разные артикулы.

БП-6. Цена должна задаваться в рублях. Нулевая цена допустима; отрицательная и неоговорённое округление введённой цены не допускаются.

БП-7. Остаток должен отражать целое число единиц товара. Нулевой остаток не удаляет запись из каталога, но исключает её из отбора по наличию.

БП-8. Совместный отбор должен включать только товары, удовлетворяющие всем заданным условиям. Ценовые границы должны включать равные им значения.

БП-9. Идентификатор и дата создания товара не должны меняться при редактировании. Дата изменения должна назначаться автоматически при изменении данных.

БП-10. Ошибка ввода или нарушение правила уникальности не должны приводить к частичному сохранению операции.

БП-11. Просмотр карточки или страницы подтверждения не должен удалять данные. Удаление допускается только после отдельного подтверждённого действия менеджера.

БП-12. Переименование категории и перевод товара в другую категорию должны изменять существующие связи без создания копии товара.

| ОГР-12 | Служебные данные | Идентификаторы и временные отметки должны формироваться системой; пользователь не должен менять их через формы ввода. |
| ОГР-13 | Числовые пределы | Значения вне диапазона выбранного при проектировании типа должны отклоняться до сохранения с объяснением ошибки. |
| ОГР-14 | Пользователи и доступ | Локальная работа одного менеджера. Публичный доступ, роли и многопользовательский режим не требуются. |
| ОГР-15 | Предметная область | Ведение каталога и текущих остатков. Заказы, расчёты с покупателями, доставка и учёт движений запасов находятся вне границ модуля. |

## Нефункциональные требования

НФТ-1. Серверная часть должна запускаться в целевой среде разработки и демонстрации; обязательные программные компоненты и команды установки должны быть описаны в инструкции.

НФТ-2. Зафиксированные записи должны сохраняться после штатной остановки и повторного запуска. Ошибка незавершённого изменения не должна нарушать ранее сохранённые данные.

НФТ-3. Интерфейс и сообщения должны быть на русском языке. Обязательные поля должны быть обозначены. Сообщение об отказе должно указывать причину и способ исправления ввода.

НФТ-4. Основные действия должны быть доступны на настольном и узком экране. Широкие таблицы не должны вынуждать прокручивать всю страницу по горизонтали. Основные формы должны работать без JavaScript.

НФТ-5. Данные пользователя не должны исполняться как разметка, сценарий или команда обращения к базе. Проверка в браузере не должна заменять проверку на стороне сервера.

НФТ-6. Вместе с модулем должны быть предоставлены исходный код, сведения о зависимостях и инструкции запуска и проверки.

НФТ-7. Система должна корректно хранить и выдавать постранично не менее 1000 товаров. Время отклика и предел одновременных обращений должны определяться отдельно при изменении области применения.

НФТ-8. Испытания с созданием, изменением и удалением записей должны выполняться на тестовых данных отдельно от рабочего каталога.

| СХ-8 | Сетевой режим | Локальное HTTP-взаимодействие браузера и сервера. Адрес и порт должны задаваться в инструкции; внешняя публикация не требуется. |
| СХ-9 | Хранение | Товары, категории и их связи должны сохраняться между запусками независимо от состояния страницы браузера. |
| СХ-10 | Обработка изменений | Связанные изменения должны сохраняться целиком либо отменяться при ошибке без частичного результата. |
| СХ-11 | Расчётный объём | Для учебной эксплуатации должна предусматриваться работа с каталогом не менее 1000 товаров и постраничным выводом. |
| СХ-12 | Аппаратная среда | Компьютер должен обеспечивать запуск серверной среды и браузера и иметь место для зависимостей, базы и копий данных. Числовые минимумы должны уточняться при выборе средств разработки. |
| СХ-13 | Зависимость от интернета | После установки обязательных компонентов основные операции локального каталога не должны требовать загрузки внешних ресурсов. |
| СХ-14 | Поставка | Исходники модуля, инструкции установки и запуска, описание зависимостей и программа приёмочных проверок. |

## Порядок приёмки

После разработки модуль должен проверяться по сценариям из таблицы. Для каждого сценария должны записываться условия запуска и полученный результат. При несовпадении с ожидаемым результатом должна фиксироваться ошибка и назначаться повторная проверка после исправления.

| Код | Сценарий | Ожидаемый результат |
|---|---|---|
| ПР-1 | Первый запуск | Пустой каталог открывается без ошибки; доступны действия создания категории и товара. |
| ПР-2 | Категории | Допустимая категория создаётся и переименовывается; дубликат имени отклоняется. |
| ПР-3 | Добавление товара | После ввода названия, артикула, категории, цены и остатка запись появляется в списке и карточке. |
| ПР-4 | Изменение товара | Новые значения сохраняются, идентификатор и дата создания не меняются. |
| ПР-5 | Ошибочный ввод | Пустое название, неверная цена, дробный остаток и повторный артикул отклоняются; ввод и прежние записи сохраняются. |
| ПР-6 | Защита категории | Категория с товарами не удаляется; причина отказа объясняется. |
| ПР-7 | Поиск | Фрагмент русского названия находится независимо от регистра; специальные символы ищутся буквально. |
| ПР-8 | Совместный отбор | Категория, цена и наличие применяются одновременно; равные ценовым границам значения включаются. |
| ПР-9 | Сортировка и страницы | Порядок соответствует выбору, равные значения не создают неоднозначность; при переходе сохраняются условия. |
| ПР-10 | Удаление | Отмена не изменяет каталог; подтверждение удаляет только выбранную запись. |
| ПР-11 | Повторный запуск | Сохранённые товары, категории и изменения остаются доступными. |
| ПР-12 | Объём каталога | На тестовом наборе не менее 1000 товаров проверяются число результатов, страницы и отбор. |
| ПР-13 | Браузерный интерфейс | Проверяются настольный и узкий экран, подписи, сообщения и основные формы без JavaScript. |
| ПР-14 | Полнота поставки | По инструкции можно установить зависимости, запустить модуль и выполнить проверки на тестовых данных. |
