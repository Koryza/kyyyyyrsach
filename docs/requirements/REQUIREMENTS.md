# Технические требования

Тема: «Разработка модуля управления каталогом товаров для интернет-магазина».

Автор: Чемоданов Никита Сергеевич.

Группа: 23ИПо8381 (ИПо-41), 4-й курс.

Назначение: локальное ведение товаров и категорий интернет-магазина. Пользователь — менеджер каталога. Авторизация, заказы, оплата, доставка и история складских движений в состав модуля не входят.

## Функциональные требования

### ПТ-1. Менеджер каталога должен иметь возможность работать с товарами:

ПТ-1.1. просматривать список товаров с названием, артикулом, категорией, ценой и текущим остатком;

ПТ-1.2. открывать карточку товара с описанием и датами создания и изменения;

ПТ-1.3. добавлять товар, указывая название, артикул, категорию, цену, остаток и необязательное описание;

ПТ-1.4. изменять сведения о товаре, включая его категорию, цену и остаток;

ПТ-1.5. удалять товар после отдельного подтверждения действия.

### ПТ-2. Менеджер каталога должен иметь возможность работать с категориями:

ПТ-2.1. просматривать список категорий с количеством товаров в каждой;

ПТ-2.2. создавать категорию, указывая название и необязательное описание;

ПТ-2.3. изменять название и описание категории;

ПТ-2.4. переходить из списка категорий к товарам выбранной категории;

ПТ-2.5. удалять категорию, если в ней нет товаров.

### ПТ-3. Менеджер каталога должен иметь возможность искать и отбирать товары:

ПТ-3.1. искать товары по части названия без учёта регистра русского текста;

ПТ-3.2. отбирать товары по категории и диапазону цены;

ПТ-3.3. показывать только товары с остатком больше нуля;

ПТ-3.4. одновременно применять поиск, фильтры и выбранную сортировку;

ПТ-3.5. сбрасывать условия отбора и возвращаться к общему списку товаров.

### ПТ-4. Менеджер каталога должен иметь возможность управлять выводом списка:

ПТ-4.1. сортировать товары по названию или цене по возрастанию и убыванию;

ПТ-4.2. выбирать порядок по времени последнего изменения, начиная с недавних;

ПТ-4.3. просматривать список страницами по 10 товаров и видеть общее число результатов;

ПТ-4.4. переходить между страницами с сохранением действующих условий поиска и отбора.

### ПТ-5. Менеджер каталога должен получать обратную связь при выполнении операций:

ПТ-5.1. видеть сообщение об успешном создании, изменении или удалении записи;

ПТ-5.2. получать объяснение ошибки ввода или конфликта с сохранением введённых значений формы;

ПТ-5.3. отменять удаление на странице подтверждения, сохраняя запись;

ПТ-5.4. получать объяснение запрета удаления занятой категории и переходить к её товарам.

## Бизнес-правила

БП-1. Каждый товар должен относиться к одной существующей категории. Категория может существовать без товаров. Переименование категории должно сохранять связи с товарами.

БП-2. Удаление категории с товарами запрещено. Сначала необходимо перенести связанные товары в другую категорию либо удалить их отдельными действиями.

БП-3. Артикул товара должен быть уникальным и содержать от 1 до 64 латинских букв, цифр, дефисов или подчёркиваний. Перед сохранением буквы приводятся к верхнему регистру.

БП-4. Название категории должно быть уникальным после удаления крайних пробелов, Unicode-нормализации NFKC и приведения регистра через casefold. Названия товаров могут совпадать.

БП-5. Название категории должно содержать от 1 до 100 символов, название товара — от 1 до 200. Описание необязательно и не должно превышать 2000 символов. Крайние пробелы удаляются.

БП-6. Цена должна быть неотрицательной. При вводе допускаются точка или запятая и не более двух дробных знаков. Избыточная точность отклоняется без округления. Цена хранится целым числом копеек в пределах SQLite.

БП-7. Остаток должен быть неотрицательным целым числом в пределах SQLite. Нулевой остаток не удаляет товар из каталога; фильтр наличия включает только позиции с остатком больше нуля.

БП-8. Нижняя граница цены не должна превышать верхнюю. Граничные значения включаются в результат. При совместном отборе товар должен удовлетворять всем выбранным условиям.

БП-9. При редактировании товара идентификатор и дата создания сохраняются, а дата изменения обновляется. Даты формируются программой в UTC.

БП-10. При отказе в сохранении из-за неверного ввода или конфликта уникальности прежние записи должны сохраняться. Неуспешная транзакция записи должна откатываться.

БП-11. Открытие страницы подтверждения не должно удалять запись. Удаление через веб-интерфейс выполняется отдельным POST-запросом после подтверждения.

БП-12. Повторная загрузка демонстрационных данных должна пропускать существующие артикулы без перезаписи товаров. Перед загрузкой в существующую базу создаётся резервная копия; новые записи добавляются одной транзакцией.

## Нефункциональные и технические требования

НФТ-1. Модуль должен работать на Python 3.12 с FastAPI, Jinja2, SQLAlchemy, SQLite и Uvicorn. Версии зависимостей должны быть закреплены в файлах установки проекта.

НФТ-2. Рабочие данные должны храниться в локальном файле SQLite и сохраняться после остановки и повторного запуска сервера. При запуске должны создаваться отсутствующие таблицы без удаления существующих записей.

НФТ-3. Доступ к каталогу должен предоставляться через HTML-страницы и JSON API с общими правилами обработки данных. Программные операции должны быть описаны в OpenAPI.

НФТ-4. Основные формы и операции каталога должны работать без JavaScript. Страницы должны использовать локальные стили и адаптироваться к узкому экрану; широкая таблица должна прокручиваться в своём контейнере.

НФТ-5. Сервер должен повторно проверять данные независимо от проверки в браузере. Пользовательский текст в HTML должен экранироваться, а значения запросов к базе — передаваться параметрами.

НФТ-6. Входные схемы должны отклонять лишние поля и недопустимые типы. JSON API должен возвращать 422 при ошибке ввода, 404 при отсутствии объекта и 409 при конфликте уникальности или связи.

НФТ-7. После успешной изменяющей HTML-операции сервер должен перенаправлять браузер на страницу результата с кодом 303. Обновление этой страницы не должно повторять сохранение формы.

НФТ-8. Проверки базы, API, HTML и загрузчика должны выполняться на отдельных временных базах, не изменяя рабочий каталог. Команды установки, запуска и проверки должны быть приведены в README.
