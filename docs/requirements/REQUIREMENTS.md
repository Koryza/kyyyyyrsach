# Технические требования

Тема: «Разработка модуля управления каталогом товаров для интернет-магазина».

Автор: Чемоданов Никита Сергеевич.

Группа: 23ИПо8381 (ИПо-41), 4-й курс.

Назначение: локальное ведение товаров и категорий интернет-магазина. Пользователь — менеджер каталога. Авторизация, заказы, оплата, доставка и история складских движений в состав модуля не входят.

## Пользовательские требования

### ПТ-1. Менеджер каталога должен иметь возможность работать с товарами:

ПТ-1.1. просматривать список товаров с названием, артикулом, категорией, ценой и текущим остатком;

ПТ-1.2. открывать карточку товара с описанием и датами создания и изменения;

ПТ-1.3. добавлять товар, указывая название, артикул, категорию, цену, остаток и необязательное описание;

ПТ-1.4. изменять сведения о товаре, включая его категорию, цену и остаток;

ПТ-1.5. удалять товар после отдельного подтверждения действия.

### ПТ-2. Менеджер каталога должен иметь возможность работать с категориями:

ПТ-2.1. просматривать список категорий с количеством товаров в каждой;

ПТ-2.2. создавать категорию, указывая название и необязательное описание;

ПТ-2.3. изменять название и описание категории;

ПТ-2.4. переходить из списка категорий к товарам выбранной категории;

ПТ-2.5. удалять категорию, если в ней нет товаров.

### ПТ-3. Менеджер каталога должен иметь возможность искать и отбирать товары:

ПТ-3.1. искать товары по части названия без учёта регистра русского текста;

ПТ-3.2. отбирать товары по категории и диапазону цены;

ПТ-3.3. показывать только товары с остатком больше нуля;

ПТ-3.4. одновременно применять поиск, фильтры и выбранную сортировку;

ПТ-3.5. сбрасывать условия отбора и возвращаться к общему списку товаров.

### ПТ-4. Менеджер каталога должен иметь возможность управлять выводом списка:

ПТ-4.1. сортировать товары по названию или цене по возрастанию и убыванию;

ПТ-4.2. выбирать порядок по времени последнего изменения, начиная с недавних;

ПТ-4.3. просматривать список страницами по 10 товаров и видеть общее число результатов;

ПТ-4.4. переходить между страницами с сохранением действующих условий поиска и отбора.

### ПТ-5. Менеджер каталога должен получать обратную связь при выполнении операций:

ПТ-5.1. видеть сообщение об успешном создании, изменении или удалении записи;

ПТ-5.2. получать объяснение ошибки ввода или конфликта с сохранением введённых значений формы;

ПТ-5.3. отменять удаление на странице подтверждения, сохраняя запись;

ПТ-5.4. получать объяснение запрета удаления занятой категории и переходить к её товарам.

## Функциональные требования

Пользовательские требования выше описывают возможности менеджера. Функциональные требования ниже задают действия системы, состав результата и реакцию на ошибочные запросы.

ФТ-1. Система должна формировать список товаров с идентификатором, названием, артикулом, категорией, ценой и остатком. JSON-ответ списка должен содержать items, total, page и page_size; HTML-страница — показывать записи, число результатов и навигацию.

ФТ-2. По идентификатору товара система должна возвращать его карточку: название, артикул, описание, категорию, цену, остаток и даты создания и изменения. При отсутствии записи система должна возвращать 404 без изменения каталога.

ФТ-3. При создании товара система должна проверять обязательные поля, существование категории и уникальность артикула, преобразовывать цену в копейки и сохранять запись с новым идентификатором и датами. JSON API должен возвращать созданный товар с кодом 201; HTML-маршрут — перенаправлять на его карточку с кодом 303.

ФТ-4. При полном изменении товара система должна принимать все обязательные редактируемые поля, проверять данные и сохранять изменения в существующей записи. Идентификатор и дата создания должны сохраняться. При конфликте артикула с другим товаром система должна возвращать 409 и сохранять прежние значения.

ФТ-5. В HTML-интерфейсе по запросу подтверждения удаления система должна показывать название и артикул товара без изменения базы. Отмена должна возвращать карточку. Только изменяющий запрос должен удалять товар; его категория должна сохраняться. JSON API должен возвращать 204 без тела, HTML-маршрут — перенаправлять в список с кодом 303.

ФТ-6. Система должна формировать список категорий с названиями и описаниями, а в HTML-интерфейсе дополнительно показывать число товаров каждой категории. Переход по этому счётчику должен открывать список товаров с выбранным category_id.

ФТ-7. При создании категории система должна удалять крайние пробелы, формировать нормализованное имя и проверять его уникальность. При допустимом вводе система должна сохранять категорию; при совпадении нормализованного имени — возвращать 409 без добавления записи.

ФТ-8. При изменении категории система должна сохранять её идентификатор и связи с товарами, обновлять название, нормализованное имя и описание. После переименования новые данные категории должны отображаться у связанных товаров. Конфликт имени должен отклоняться без частичного изменения записи.

ФТ-9. Перед удалением категории система должна проверять наличие связанных товаров. При наличии товаров изменяющий запрос должен получать 409, категория и товары должны сохраняться; HTML-страница подтверждения должна объяснять запрет и содержать ссылку на эти товары. Пустая категория должна удаляться после подтверждения.

ФТ-10. При поиске система должна преобразовывать запрос тем же способом, что и название товара: NFKC, удаление крайних пробелов и casefold. Отбор должен выполняться по вхождению строки в нормализованное название. Символы процента, подчёркивания и косой черты должны восприниматься буквально.

ФТ-11. Система должна совместно применять поиск, категорию, включительные границы цены и наличие. Наличие должно означать quantity больше нуля. Неверный диапазон должен отклоняться с кодом 422. После сброса условий система должна возвращать общий список без прежних фильтров.

ФТ-12. Система должна выбирать сортировку только из name_asc, name_desc, price_asc, price_desc и updated_desc. При совпадении основного значения записи должны дополнительно упорядочиваться по id по возрастанию. Неизвестное значение сортировки должно возвращать 422.

ФТ-13. Система должна считать общее число записей по тем же условиям, что используются для выборки, и возвращать до 10 товаров с соответствующим смещением. HTML-ссылки страниц должны сохранять поиск, фильтры и сортировку. Отправка нового набора фильтров должна начинать просмотр с первой страницы.

ФТ-14. При ошибке данных или конфликте в форме создания или редактирования система должна возвращать эту форму с исходным вводом и объяснением. После успешного создания, изменения или удаления система должна показывать соответствующее уведомление. Результат сохранения формы должен открываться отдельным GET после перенаправления 303.

ФТ-15. Система должна предоставлять десять операций JSON API для товаров и категорий и описывать их в OpenAPI. Для ошибочных запросов API должен возвращать JSON: 422 при неверном вводе, 404 при отсутствии объекта и 409 при конфликте уникальности или связи. Обращения к HTML и API должны вызывать общие операции каталога.

## Атрибуты данных

### Сущность «Категория»

Обязательность ниже относится к сохранённой записи. Системные поля заполняет приложение; пользователь вводит название и необязательное описание.

| Атрибут | Тип и обязательность | Назначение и правила |
|---|---|---|
| id | Целое; обязательный, системный | Первичный ключ. Создаётся базой и используется в связях и адресах. Через API не редактируется. |
| name | Строка; обязательный | Название категории: 1–100 символов после удаления крайних пробелов. |
| name_normalized | Текст; обязательный, служебный | Нормализованное название для сравнения. Непустое и уникальное; обновляется при переименовании. |
| description | Текст или NULL; необязательный | Описание категории, до 2000 символов. Пустой текст после удаления крайних пробелов сохраняется как NULL. |

### Сущность «Товар»

| Атрибут | Тип и обязательность | Назначение и правила |
|---|---|---|
| id | Целое; обязательный, системный | Первичный ключ. Назначается базой; при редактировании товара сохраняется. |
| name | Строка; обязательный | Название товара: 1–200 символов после удаления крайних пробелов. Совпадения названий разрешены. |
| name_normalized | Текст; обязательный, служебный | Нормализованное непустое название для поиска без учёта регистра. |
| sku | Строка; обязательный | Уникальный артикул: 1–64 латинские буквы, цифры, дефисы или подчёркивания. Хранится в верхнем регистре. |
| description | Текст или NULL; необязательный | Описание товара, до 2000 символов. Пустое значение сохраняется как NULL. |
| category_id | Целое; обязательный | Внешний ключ на categories.id. Должен указывать на существующую категорию. |
| price_kopecks | Целое; обязательный | Цена в копейках от 0 до 9223372036854775807. Внутреннее представление базы. |
| quantity | Целое; обязательный | Текущий остаток от 0 до 9223372036854775807. В модели значение по умолчанию равно 0. |
| created_at | Дата и время; обязательный, системный | Время создания в UTC. Заполняется автоматически и сохраняется при редактировании. |
| updated_at | Дата и время; обязательный, системный | Время последнего изменения в UTC. Обновляется моделью при изменении записи. |

### Представление данных в API

В запросе создания и полного изменения товара обязательны name, sku, category_id, price и quantity. Описание необязательно. Наличие значения по умолчанию quantity в модели не отменяет обязательность этого поля в JSON-запросе.

Цена передаётся полем price как строка рублей, например «49.90», и преобразуется сервером в price_kopecks. В ответе дополнительно возвращается category_name — название связанной категории. Это поле не хранится отдельным столбцом товара.

Поля id, name_normalized, price_kopecks, created_at и updated_at не принимаются как редактируемые поля. Время в JSON обозначается как UTC; SQLite хранит дату и время без встроенного часового пояса по соглашению приложения.

## Бизнес-правила

БП-1. Каждый товар должен относиться к одной существующей категории. Категория может существовать без товаров. Переименование категории должно сохранять связи с товарами.

БП-2. Удаление категории с товарами запрещено. Сначала необходимо перенести связанные товары в другую категорию либо удалить их отдельными действиями.

БП-3. Артикул товара должен быть уникальным и содержать от 1 до 64 латинских букв, цифр, дефисов или подчёркиваний. Перед сохранением буквы приводятся к верхнему регистру.

БП-4. Название категории должно быть уникальным после удаления крайних пробелов, Unicode-нормализации NFKC и приведения регистра через casefold. Названия товаров могут совпадать.

БП-5. Название категории должно содержать от 1 до 100 символов, название товара — от 1 до 200. Описание необязательно и не должно превышать 2000 символов. Крайние пробелы удаляются.

БП-6. Цена должна быть неотрицательной. При вводе допускаются точка или запятая и не более двух дробных знаков. Избыточная точность отклоняется без округления. Цена хранится целым числом копеек в пределах SQLite.

БП-7. Остаток должен быть неотрицательным целым числом в пределах SQLite. Нулевой остаток не удаляет товар из каталога; фильтр наличия включает только позиции с остатком больше нуля.

БП-8. Нижняя граница цены не должна превышать верхнюю. Граничные значения включаются в результат. При совместном отборе товар должен удовлетворять всем выбранным условиям.

БП-9. При редактировании товара идентификатор и дата создания сохраняются, а дата изменения обновляется. Даты формируются программой в UTC.

БП-10. При отказе в сохранении из-за неверного ввода или конфликта уникальности прежние записи должны сохраняться. Неуспешная транзакция записи должна откатываться.

БП-11. Открытие страницы подтверждения не должно удалять запись. Удаление через веб-интерфейс выполняется отдельным POST-запросом после подтверждения.

БП-12. Повторная загрузка демонстрационных данных должна пропускать существующие артикулы без перезаписи товаров. Перед загрузкой в существующую базу создаётся резервная копия; новые записи добавляются одной транзакцией.

| ОГР-8 | Поиск и цена отбора | Строка поиска — до 200 символов. Каждая ценовая граница — до 32 символов, с правилами разбора цены; нижняя не превышает верхнюю. |
| ОГР-9 | Пагинация | Номер страницы от 1 до 922337203685477580. Размер страницы фиксирован: 10 товаров. |
| ОГР-10 | Сортировка | Разрешены только name_asc, name_desc, price_asc, price_desc и updated_desc. При равенстве значений используется id. |
| ОГР-11 | Связи и удаление | Один товар относится к одной категории. Внешний ключ RESTRICT запрещает удаление занятой категории; каскадное удаление её товаров не применяется. |
| ОГР-12 | Состав запросов | Лишние поля отклоняются. quantity и category_id в JSON принимаются строгими целыми числами; строки, логические и дробные значения не подменяют эти типы. |
| ОГР-13 | Изменение записи | PUT требует полный набор обязательных полей товара. Частичное обновление PATCH не реализовано. |
| ОГР-14 | Объём модуля | Локальный каталог одного менеджера. Авторизации, ролей, заказов, оплаты, доставки, иерархии категорий и журнала складских операций нет. |
| ОГР-15 | Развитие схемы | Создание таблиц при запуске не изменяет существующую схему. Автоматические миграции не реализованы. |

## Нефункциональные требования

НФТ-1. Совместимость среды: приложение должно работать на Python 3.12 в предусмотренных проектом средах macOS и Linux. Зависимости должны устанавливаться в отдельное виртуальное окружение из закреплённых файлов проекта.

НФТ-2. Сохранность данных: зафиксированные записи обычной SQLite-базы должны сохраняться после штатной остановки и повторного запуска сервера. Отклонённая запись не должна оставлять частично сохранённые изменения.

НФТ-3. Удобство использования: поля форм должны иметь видимые подписи, а ошибки — текстовое объяснение причины отказа. После ошибки корректно заполненные поля не должны очищаться.

НФТ-4. Адаптивность: страницы должны подстраиваться под узкий экран, а широкая таблица — прокручиваться в своём контейнере. Основные формы и операции каталога должны оставаться доступными без JavaScript.

НФТ-5. Безопасность обработки ввода: сервер не должен полагаться только на проверку браузера. Пользовательский текст в HTML должен экранироваться, а значения запросов к базе — передаваться параметрами.

НФТ-6. Изолированность проверки: тесты базы, API, HTML и загрузчика должны использовать отдельные временные базы без изменения рабочего каталога. Команды установки, запуска и проверки должны быть приведены в README.

НФТ-7. Сопровождаемость: модели хранения, входные схемы, операции каталога и представления должны быть разделены по модулям. HTML и JSON API должны использовать общий слой операций без дублирования правил записи.

НФТ-8. Доступность локального интерфейса: после установки зависимостей основные страницы каталога должны работать без загрузки стилей и скриптов из внешних CDN. Внешние файлы Swagger допускаются только для интерфейса документации API.
